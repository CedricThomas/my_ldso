📦 Pourquoi des bibliothèques partagées existent ?

Sans partage coûteux

Chaque programme contient sa propre copie de libc, libm, etc.

  • Le binaire grossit vite
  • La même librairie est dupliquée en mémoire
  • Une mise à jour impose de tout recompiler
vs

Avec partage mieux

Le code commun vit dans des fichiers .so chargés au lancement

  • Le programme principal reste petit
  • Les pages de code peuvent être partagées
  • Mettre à jour une bibliothèque profite à tous

💡 Gardons un exemple simple en tête

On va suivre un mini programme hello qui appelle puts("hello"). Le but de la présentation est simple : Découvrir comment cet appel finit par fonctionner 

$ cat hello.c 
// hello.c
#include <stdio.h>

int main(void) {
    puts("hello");
    return 0;
}

$ gcc hello.c -o hello
$ ./hello
hello
  • Le binaire hello ne contient pas l'implémentation de puts()
  • Il déclare simplement : "j'aurai besoin de la lib C au démarrage"
  • Un composant invisible va trouver cette librairie et brancher les appels de fonctions aux bonnes adresses
  • Ce composant, c'est ld.so

🎯 main() is a lie

Avant main(), plusieurs acteurs apparaissent déjà dans le démarrage du programme.

kernel
→

→
_start() runtime C
→
main() votre code
  • Le kernel est l'acteur externe qui lance le processus
  • ld.so est le loader dynamique qui résout les dépendances dynamiquement
  • _start() est le vrai point d'entrée d'un ELF mettant en place le runtime du binaire
  • main() arrive en bout de chaîne et c'est le point d'entrée de votre programme
  • Chaque couche prépare la suivante

🦸 Le super-pouvoir de ld.so

# Le kernel pré-charge le binaire en mémoire
# puis délègue la relocation à ld.so
$ ./hello
hello

# ld.so charge lui même le binaire
# puis s'occupoe de la relocation
$ ./ld.so ./hello
hello

ld.so est autonome

  • Le vrai super-pouvoir de ld.so est qu'il peut charger le binaire principal lui-même, pas seulement les bibliothèques.
  • C'est ce point de vue qui rend visibles toutes les étapes internes du loader, au lieu de les laisser cachées derrière un mapping côté kernel.
Pour le reste de la présentation, on assumera que ld.so ouvre le programme cible lui même.

⚖️ Binaire principal vs bibliothèque .so

Même format ELF, mais pas le même rôle. L'un est le point de départ du processus; l'autre est une dépendance chargée en cours de route.

Exécutable principal

  • Qui charge le binaire : le kernel / ld.so
  • Rôle : fournir le point d'entrée du programme
  • Ce qu'il contient souvent : un chemin vers l'interpréteur dynamique et une liste de dépendances
  • Particularité : un point d'entrée de l'exécutable est documenté dans le header de l'ELF
vs

Bibliothèque partagée

  • Qui charge le binaire : ld.so, depuis le runtime d'un autre ELF
  • Rôle : apporter du code, des données et des symboles réutilisables
  • Ce qu'elle contient souvent : des exports, des imports et ses propres relocations
  • Particularité : un segment DT_INIT permet d'initialiser la bibliothèque

🧩 Deux familles de segments utiles

Après avoir parcouru la Program Header Table, le loader splitte son travail en deux branches.

📦 Segments mapper

Les blocs qui deviennent de la mémoire : code exécutable, constantes et données.

  • Chaque PT_LOAD contient une partie du fichier → on la mappe à une adresse
  • Chacun avec ses permissions (R | W | X)
🔗 Dynamique relier

Le bloc PT_DYNAMIC qui guide le linkage dynamique : bibliothèques, symboles et relocations.

  • La liste des bibliothèques à chercher et à charger
  • La table de symboles/fonctions — pour savoir où se trouve puts dans la lib C
  • Les relocations — les "trous" à combiner pour que tout marche

Idée à retenir : la table a ouvert deux chantiers pour le loader — on suit l'un après l'autre.

⚡ Premier piège : pas de libc pour construire libc

Le chargeur démarre très tôt. Donc au moment où il tourne, il ne peut pas encore s'appuyer sur les conforts habituels.

Ce qui manque au départ contraintes

  • Pas de malloc() prêt à l'emploi
  • Pas de printf() confortable
  • Pas de couches haut niveau autour des syscalls
  • Très peu d'outils de debug
  • Presque aucun filet de sécurité

Donc il faut se débrouiller

  • Compiler en mode freestanding
  • Faire des syscalls directs au kernel
  • Écrire un mini printf si besoin
  • Écrire un mini allocateur si besoin
  • Garder le code simple et robuste
// Point d'entrée réel du chargeur :
.global _start
_start:
    xor %ebp, %ebp
    mov %rsp, %rdi        // récupérer la pile initiale
    call ldso_main        // commencer sans libc

🔀 Relocation = remplacer des trous par de vraies adresses

Le programme appelle des fonctions externes. Mais où se trouvent-elles exactement ?

La GOT (Global Offset Table)

Une petite table qui vit dans la section .got.plt du fichier. Chaque case est un trou — un emplacement réservé pour l'adresse d'une fonction externe.

0x00000000 → case pour puts
0x00000000 → case pour malloc
0x00000000 → case pour __libc_start_main

Le compilateur ne connaît pas les adresses réelles. Il a préparé la GOT avec des zéros — le loader viendra combler les trous.

Comment le code appelle une fonction
call 0x401000 → le programme appelle la PLT
jmp GOT[n] → la PLT lit la GOT et saute
0x7f...a1b2c3 → l'adresse réelle dans libc

La PLT (Procedure Linkage Table) est un trampoline : le programme ne connaît pas l'adresse réelle, il saute via la GOT. Le loader a juste besoin de remplir la GOT avec les bonnes valeurs.

En résumé
GOT[n] = 0 → le loader cherche puts dans libc → GOT[n] = &puts

  • La recherche suit les chemins usuels de Linux : RPATH, LD_LIBRARY_PATH, RUNPATH, chemins système
  • Le chargeur prépare ensuite un saut vers l'entry point du programme, pas directement vers main()

Branchement final

  • Chaque symbole externe est recherché dans la link map
  • Les emplacements marqués sont corrigés en mémoire
  • Le chargeur garde une vue d'ensemble des bibliothèques déjà chargées
  • Puis il saute enfin vers l'adresse d'entrée du programme, où le CRT startup finira par appeler main()

📊 La structure la plus importante : la link map

Chaque bibliothèque chargée obtient une entrée dans cette liste chaînée — c'est le registre central du loader.

Les Structures de données
/* Une entrée par DSO chargé */
struct link_map {
l_name char* // "libc.so.6"
l_addr Elf64_Addr // adresse de base
l_sym Elf64_Sym* // ↓ table de symboles
l_next, l_prev link_map* // ◄ pointeurs de navigation ►
};
/* Une entrée = un symbole / une fonction */
struct Elf64_Sym {
st_name uint32_t // offset dans une liste de noms
st_value Elf64_Addr // offset de la fonction dans la lib
};
La link map du hello
./hello 0x401000 —
◀▶
libc.so.6 0x7f...a000 puts
◀▶
libm.so.6 0x7f...6000 cos, sin, …
ex: comment on trouve puts dans libc
l_addr = BASE — où le kernel a placé libc en mémoire
st_value de puts = OFFSET — la distance de puts depuis le début de libc
adresse réelle de puts = BASE + OFFSET
3 rôles : dédup (déjà chargé ?), recherche (où est puts ?), calcul d'adresse (base + offset).

🔎 Résoudre un symbole

On permet un appel valide vers puts.

Le Problème
0x4011a8 0x00000000 GOT[puts] <— trou à combler

Le binaire contient une relocation sur puts

1
Parcourir la link map
./hello → libc.so.6 → libm.so.6 → NULL
libc.so.6 contient puts → ✅
2
Lire le symbole
puts.st_value = 0x48a30 (offset dans libc)
3
Calculer l'adresse absolue
l_addr + st_value = 0x7f...a000 + 0x48a30 = 0x7f...48a30
4
Patcher la GOT
*0x4011a8 ← 0x7f...48a30 — slot comblé ✓
Le cœur du linker n'est pas de mapper des pages — c'est de faire correspondre un nom à une adresse.

🪟 Même problème, autre monde : Linux vs Windows

Linux / ELF

  • Format : ELF
  • Quoi charger : segments + section dynamique
  • Quoi résoudre : symboles externes
  • Quoi patcher : relocations ELF
  • Qui saute à la fin : ld.so vers l'entry point
vs

Windows / PE

  • Format : PE
  • Quoi charger : sections + import table
  • Quoi résoudre : imports de DLL
  • Quoi patcher : base relocations
  • Qui saute à la fin : loader Windows vers l'entry point

Une fois le pipeline ELF compris, la comparaison devient simple : même problème général, vocabulaire et formats différents.

🔁 Pourquoi ELF m'a aidé à écrire un loader PE minimaliste

  • J'avais déjà un modèle mental stable : charger des blocs, trouver des dépendances, résoudre des noms, patcher des adresses, sauter à l'entry point.
  • Le format change entre ELF et PE, mais les questions du loader restent presque les mêmes.
  • Comprendre clairement la frontière kernel / loader / runtime m'a évité de mélanger les responsabilités.
  • ELF m'a donc servi de terrain d'apprentissage pour généraliser ensuite vers PE.
