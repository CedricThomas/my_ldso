📦 Pourquoi des bibliothèques partagées existent ?

Sans partage coûteux

Chaque programme contient sa propre copie de libc, libm, etc.

  • Le binaire grossit vite
  • Le même code est dupliqué en mémoire
  • Une mise à jour impose de tout recompiler
vs

Avec partage mieux

Le code commun vit dans des fichiers .so chargés au lancement

  • Le programme principal reste petit
  • Les pages de code peuvent être partagées
  • Mettre à jour une bibliothèque profite à tous

💡 Gardons un exemple simple en tête

Le but: découvrir comment hello peut utiliser puts("hello")

hello.c
#include <stdio.h>

int main(void) {
    puts("hello");
    return 0;
}
$ gcc hello.c -o hello
$ ./hello
hello
  • Le binaire ELF hello ne contient pas l'implémentation de puts()
  • Il déclare simplement : "j'aurai besoin de la lib C au démarrage"
  • Un composant invisible va trouver cette librairie et la brancher
  • Ce composant, c'est ld.so

⚡ Premier piège : pas de libc avant l'initialisation de libc

Le chargeur démarre très tôt. Donc au moment où il tourne, il ne peut pas encore s'appuyer sur les conforts habituels.

Ce qui manque au départ contraintes

  • Pas de malloc() prêt à l'emploi
  • Pas de printf() confortable
  • Pas de couches haut niveau autour des syscalls
  • Très peu d'outils de debug
  • Presque aucun filet de sécurité

Donc il faut se débrouiller

  • Compiler sans librairies dynamiques
  • Faire des syscalls directs au kernel
  • Écrire un mini printf si besoin
  • Écrire un mini allocateur si besoin
  • Garder le code simple et robuste
// Pas de main classique pour le loader dynamique !
.global _start
_start:
    xor %ebp, %ebp
    mov %rsp, %rdi
    call ldso_main        // appel du main

🎯 main() is a lie

Avant main(), plusieurs acteurs interviennent !

kernel
→
ld.so linking
→
_start() runtime C
→
main() votre code
  • Le kernel lance le processus
  • ld.so est le loader dynamique
  • _start() est le point d'entrée du binaire
  • main() c'est le début de votre code applicatif,
  • Chaque couche prépare la suivante

🦸 Le super-pouvoir de ld.so

# Le kernel mappe l’exécutable en mémoire
# mappe ld.so, puis saute dans ld.so
$ ./hello
hello

# ld.so charge lui même le binaire
# puis s'occupe de la relocation
$ ./ld.so ./hello
hello

ld.so est polyvalent

  • En général, le kernel charge le binaire en mémoire et lance le loader demandé par le binaire.
  • Cependant, ld.so peut aussi charger le binaire principal lui-même, pas seulement les bibliothèques.
Pour le reste de la présentation, on assumera que ld.so ouvre le programme cible lui même.

⚖️ Binaire principal vs bibliothèque .so

Même format ELF, mais pas le même rôle.

Exécutable principal

  • Qui charge le binaire : le kernel / ld.so
  • Rôle : fournir le point d'entrée du programme
  • Ce qu'il contient souvent : un chemin vers le loader dynamique et une liste de dépendances

Bibliothèque partagée

  • Qui charge le binaire : ld.so
  • Rôle : apporter du code et des variables réutilisables
  • Ce qu'elle contient souvent : des exports de fonctions et une liste de dépendances

⛏️ Comment le loader navigue dans un ELF ?

Un ELF c'est comme un jeu d'enquête : chaque couche répond à une question et en pose deux nouvelles.

[2]

[n]

1

On récupère la carte

Le loader lit le début du fichier, puis récupère un offset vers la table suivante.

2

On lit la carte

Le loader additionne l'offset depuis le début du fichier et arrive au début de la Program Header Table.

3

Le loader parcourt les entrées une par une, recupère les offsets des segments utiles et en sauvegarde les adresses.

🧩 Deux familles de segments utiles

Après avoir parcouru la Program Header Table, le loader sépare son travail en deux branches.

📦 Segments PT_LOAD mapper

Ce que le loader va mapper en mémoire :

  • Code R | X — les instructions
  • Constantes R — données en lecture seule
  • Données R | W — variables globales
🔗 Segment PT_DYNAMIC relier

Ce que le loader va lire pour faire le lien :

  • Dépendances — les .so à charger (libc.so...)
  • Symboles — les noms externes (puts, malloc...)
  • Relocations — les trous à combler

Idée à retenir : la table a ouvert deux chantiers pour le loader — on suit l'un après l'autre.

📊 La structure la plus importante : la link map

Chaque bibliothèque chargée obtient une entrée dans cette liste chaînée — c'est le registre central du loader.

Les Structures de données
/* Une entrée par DSO chargé */
struct link_map {
l_name char* // "libc.so.6"
l_addr Elf64_Addr // adresse de base
l_sym Elf64_Sym* // ↓ table de symboles
l_next, l_prev link_map* // ◄ pointeurs de navigation ►
};
/* Une entrée = un symbole / une fonction */
struct Elf64_Sym {
st_name uint32_t // offset dans une liste de noms
st_value Elf64_Addr // adresse relative de la fonction
};
La link map de hello
./hello 0x401000 —
◀▶
libc.so.6 0x7f...a000 puts
ex: comment on trouve puts dans libc
l_addr = BASE — où le loader a placé libc en mémoire
st_value de puts = OFFSET — la distance de puts depuis le début de libc
adresse réelle de puts = BASE + OFFSET
3 rôles : partage de code, recherche de symboles, calcul d'adresses.

🔀 Relocation = remplacer des trous par de vraies adresses

La GOT (Global Offset Table)

Une petite liste qui a été mappé plus tôt par le loader. Un emplacement est réservé pour chaque fonction externe.

0x???????? → case pour puts
0x???????? → case pour malloc
0x???????? → case pour __libc_start_main

Quand le compilateur ne connaît pas une adresse réelle il ajoute une entrée pour elle dans la GOT — le loader viendra la mettre à jour.

La PLT (Procedure Linkage Table)

Les adresses de fonctions dans la GOT ne sont pas exploitable sans un petit wrapper autour pour les exécuter.

call 0x401000 → le programme appelle la PLT
jmp GOT[n] → la PLT lit la GOT et saute
0x7f...a1b2c3 → l'adresse réelle dans libc

La PLT est un trampoline : son role est de sauter sur une adresse de fonction précisé dans la GOT.

Vrai role de la GOT
0x???????? → fonction_externe function
0x???????? → variable_externe data

La GOT peut servir pour plusieurs type de symboles externes.

En résumé
GOT[n] = ? → le loader cherche puts dans libc → GOT[n] = &puts

Le Problème
0x4011a8 0x???????? GOT[puts]

Le binaire contient une relocation sur puts

1
Parcourir la link map
./hello → libc.so.6 → NULL
libc.so.6 contient puts → ✅
2
Lire le symbole
puts.st_value = 0x48a30 (offset dans libc)
3
Calculer l'adresse absolue
l_addr + st_value = 0x7f...a000 + 0x48a30 = 0x7f...48a30
4
Patcher la GOT (Global Offset Table)
*0x4011a8 ← 0x7f...48a30 — slot comblé ✓

🪟 Même problème, autre monde : Linux vs Windows

Linux / ELF

  • Format : ELF
  • Quoi charger : segments PT_LOAD et PT_DYNAMIC
  • Quoi résoudre : symboles externes
  • Quoi patcher : relocations ELF
  • Qui saute à la fin : ld.so vers l'entry point
vs

Windows / PE

  • Format : PE (.exe)
  • Quoi charger : ?
  • Quoi résoudre : imports de DLL
  • Quoi patcher : ?
  • Qui saute à la fin : loader Windows vers l'entry point

Même problème. Autre vocabulaire. Le pipeline est similaire.

💡 ASM is ASM

Le format fichier n'est qu'une enveloppe. Sous le capot, c'est toujours la même machine.

La réalité CPU

  • Le CPU ne connaît ni ELF ni PE.
  • Il exécute des instructions x86_64, point.

Un mov rax, rcx compilé sur Windows est bit-identique au même sur Linux.

L'idée implication

  • Un binaire PE pourrait tourner sur Linux.
  • Il lui manque une couche de traduction et surtout un loader !
